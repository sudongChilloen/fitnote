## 1. 서비스 개요

PT 센터/헬스장 회원을 위한 **운동 기록 + PT 알림장 + 기구 기반 운동 추천** 서비스.

### 역할 구조

```
CENTER_ADMIN (헬스장 관리자)
   ├─ 헬스장 등록, 트레이너 초대
   ├─ PT 상품(가격/횟수) 등록·관리
   └─ (선택) 헬스장 보유 기구 프리셋 등록
        │
        ▼
TRAINER (N명)
   ├─ 배정된 회원 관리
   ├─ 알림장 작성 → 회원에게 FCM 알림
   └─ PT 완료 처리 → 잔여 횟수 자동 차감
        │
        ▼
MEMBER (회원)
   ├─ 운동/식단/신체 기록
   └─ 알림장 확인
```

`CenterMembership` 한 테이블에 role 을 통합하고, 자기참조
`assignedTrainerMembershipId` 로 회원 → 담당 트레이너를 배정한다.

### 핵심 설계 판단

| 결정                                             | 이유                                                                                                   |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **기구 카탈로그는 플랫폼이 시드로 제공**         | 덤벨·바벨·머신 등은 어느 헬스장이나 이름이 같다. 헬스장이 등록해줄 때까지 기다리면 콜드스타트에 걸린다 |
| **기본값 = 전체 운동 노출**                      | "내가 쓸 수 있는 기구 체크"를 가입 조건으로 두면 이탈한다. 헬스장 연결은 나중에 옵션으로               |
| **User 는 헬스장 없이도 존재 가능**              | 헬스장 고객이 0명이어도 개인 사용자로 서비스가 돌아가야 한다                                           |
| **웹소켓 미도입, FCM 만 사용**                   | 알림장·PT 일정은 비동기 이벤트다. 실시간 양방향 통신이 필요한 기능이 없다                              |
| **AI 는 `AiAnalysis` 범용 테이블로 자리만 확보** | LLM 비용 부담이 커서 MVP 에서 제외. 나중에 붙일 때 스키마 변경 불필요                                  |

## 3. 배포 설정 (Vercel)

### 3-1. pnpm 락파일 문제 — 해결 완료

프로젝트를 pnpm 으로 시작했다가 npm 으로 옮겼는데 `pnpm-lock.yaml` 이 커밋에 남아
있었다. Vercel 은 pnpm 락파일을 먼저 감지해 `--frozen-lockfile` 로 설치를 시도하고,
락파일이 `package.json` 과 달라 실패했다.

```
ERR_PNPM_OUTDATED_LOCKFILE
Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up to date
```

**조치**

1. `pnpm-lock.yaml` 삭제 + git 추적 해제 (`package-lock.json` 만 유지)
2. `package.json` 에 패키지 매니저 고정 명시

```json
"packageManager": "npm@11.6.2"
```

> 락파일은 **하나만** 커밋해야 한다. 두 개가 있으면 로컬(npm)과 CI(pnpm)가
> 서로 다른 의존성 트리로 동작한다.

### 3-2. 환경변수 — 배포 전 반드시 설정

환경변수 없이 빌드하면 **page data 수집 단계에서 실패**한다.
`lib/prisma.ts`, `app/lib/jwt.ts` 가 모듈 로드 시점에 검사하기 때문이다.

```
Error: Failed to collect page data for /api/exercises
  [cause]: Error: DATABASE_URL is not defined
```

Vercel > Settings > Environment Variables 에 등록할 값:

| 변수             | 용도         | 비고                                           |
| ---------------- | ------------ | ---------------------------------------------- |
| `DATABASE_URL`   | 앱 런타임    | Supabase **pgbouncer 6543** (transaction 모드) |
| `DIRECT_URL`     | 마이그레이션 | Supabase **5432** (session 모드)               |
| `SESSION_SECRET` | JWT 서명     | `openssl rand -base64 32`                      |

사진(알림장 첨부)을 쓰려면 아래도 필요하다. 없으면 사진 영역이 "저장소가 설정되지
않았어요" 로 바뀌고 나머지 기능은 그대로 동작한다.

| 변수                        | 용도              | 비고                                     |
| --------------------------- | ----------------- | ---------------------------------------- |
| `SUPABASE_URL`              | Storage REST 주소 | `https://<project-ref>.supabase.co`      |
| `SUPABASE_SERVICE_ROLE_KEY` | 서명 주소 발급    | **서버 전용.** 브라우저로 나가면 안 된다 |
| `SUPABASE_PHOTO_BUCKET`     | 버킷 이름         | 기본값 `fitnote-photos`                  |

버킷은 새 환경에서 한 번만 만들면 된다.

```bash
npx tsx --conditions=react-server scripts/setup-storage.mts
```

> **연결 이원화가 중요하다.** 서버리스는 커넥션이 폭증하므로 런타임은 pooler(6543)를
> 써야 하고, 마이그레이션은 advisory lock 때문에 direct(5432)를 써야 한다.
> `prisma.config.ts` 의 datasource 가 `DIRECT_URL` 을 보는 이유다.

### 4-3. 인증

Next.js 공식 가이드의 **optimistic / secure 2단계 패턴**을 따랐다.

```
proxy.ts        쿠키의 JWT 서명만 확인 (낙관적, DB 접근 없음)
    ↓
app/lib/dal.ts  실제 DB 조회로 세션 유효성 검증 (실질적 방어선)
```

| 파일                     | 역할                                                                      |
| ------------------------ | ------------------------------------------------------------------------- |
| `app/lib/jwt.ts`         | JWT 서명/검증 **전용**. Prisma 의존 없음                                  |
| `app/lib/session.ts`     | `createSession` / `deleteSession`                                         |
| `app/lib/dal.ts`         | `getOptionalSession` / `verifySession` / `getCurrentUser` / `requireUser` |
| `app/lib/definitions.ts` | zod 스키마                                                                |
| `app/actions/auth.ts`    | signup / login / logout Server Actions                                    |
| `proxy.ts`               | 라우트 보호                                                               |

**jwt.ts 를 분리한 이유**: `proxy.ts` 가 `session.ts` 를 import 하면 Prisma 와
`server-only` 가 proxy 번들에 딸려 들어간다. `jwt.ts` 는 `jose` 만 의존한다.

보안 처리:

- 쿠키에는 원본 토큰이 아니라 `{ userId, sessionId }` JWT 를 담는다
- DB 에는 별도 랜덤 토큰의 **sha256 해시만** 저장 → 유출돼도 세션 복원 불가
- 로그인 실패 메시지를 통일해 **계정 존재 여부가 드러나지 않도록** 함
- 쿠키: `httpOnly`, `sameSite=lax`, 프로덕션에서 `secure`

v2 프로토타입(v0 생성물)에서 **프론트만 선별 이식**했다.

| 가져온 것         | 내용                                                                             |

**의도적으로 버린 것**

- `next.config.mjs` 의 `typescript.ignoreBuildErrors: true` — 타입 에러를 덮는다
- **아이콘 4종** — `icon.svg` 를 열어보니 FitNote 가 아니라 **v0.app 로고**였다.
  파비콘은 별도 제작 필요
- v2 의 `Role = 'member' | 'trainer'` 2역할 토글 — 확정 기획(3역할)과 맞지 않는다

한글 폰트 처리: Geist 에 한글 글리프가 없어 폴백을 명시했다.

```css
--font-sans:
  var(--font-geist-sans), "Apple SD Gothic Neo", "Malgun Gothic", sans-serif;
```

#### 색: 파스텔 주황을 "버튼 색"으로 쓸 수 없다

포인트는 파스텔 주황, 기본은 어두운 색으로 정했다. 그런데 파스텔 주황 위에
흰 글씨는 **어떤 밝기를 골라도 WCAG AA(4.5:1)를 넘지 못한다.** oklch 명도를
0.62~~0.78 로 바꿔가며 sRGB 로 변환해 직접 계산해 봤고 대비는 2.0~~3.8 에 머물렀다.
밝기를 더 낮추면 대비는 오르지만 그 시점엔 이미 파스텔이 아니다.

그래서 색을 하나로 쓰지 않고 **역할을 쪼갰다.**

| 토큰           | hex       | 역할                                           | 대비                        |
| -------------- | --------- | ---------------------------------------------- | --------------------------- |
| `primary`      | `#261d18` | 기본 버튼·강조 배경 (웜 차콜)                  | 흰 글씨 15.8:1              |
| `brand`        | `#f7a062` | **면을 채울 때만** — 진행바, 배지, 아이콘 타일 | (글자 금지)                 |
| `brand-strong` | `#a84811` | **글자·아이콘용** 주황                         | 흰 배경 5.8:1               |
| `accent`       | `#ffecdc` | 옅은 칩 배경                                   | + `accent-foreground` 7.8:1 |
| `background`   | `#fcfaf6` | 웜 화이트 (순백을 피해 주황과 안 싸우게)       |                             |

**규칙: `brand` 위에 글자를 올리지 않는다. 주황 글자가 필요하면 `brand-strong`.**
이 규칙과 대비 수치는 `app/globals.css` 상단 주석에도 적어 뒀다.

팔레트는 `light-dark()` 로 **한 번만** 선언한다. 기존 shadcn 토큰은 `:root` /
`.dark` / `@media (prefers-color-scheme)` 3곳에 같은 변수를 중복 정의해서,
색 하나 바꾸려면 세 군데를 고쳐야 했다. Lightning CSS 가 구형 브라우저용
폴백까지 자동 생성해 주는 것을 빌드 산출물에서 확인했다.

### 4-5. 운동 API

| 엔드포인트                | 설명                                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| `GET /api/exercises`      | 목록. `search` / `bodyPart` / `difficulty` / `movementType` / `equipmentId` / `page` / `limit` |
| `GET /api/exercises/[id]` | 상세. 없으면 404                                                                               |

`server/exercises/exercise.service.ts` 에서 **공통 `exerciseInclude` + `toExerciseDto()`**
를 쓴다. 목록과 상세가 각자 매퍼를 가지면 응답 형태가 어긋나기 쉽기 때문이다.

대체 운동에는 **해당 대체 운동의 장비도 함께** 내려준다. "기구가 없어요" 흐름에서
추가 API 호출 없이 지금 쓸 수 있는 운동인지 판단하기 위해서다.

### 4-6. 운동 화면

| 경로              | 파일                                                |
| ----------------- | --------------------------------------------------- |
| `/exercises`      | `app/(user)/exercises/page.tsx` (서버 컴포넌트)     |
|                   | `exercise-filters.tsx` (클라이언트: 검색 + 필터 칩) |
|                   | `exercise-card.tsx`                                 |
| `/exercises/[id]` | `app/(user)/exercises/[id]/page.tsx`                |
| 공통              | `lib/exercise-labels.ts` — enum → 한글 라벨         |

설계 판단:

- **HTTP fetch 대신 서비스 직접 호출.** 서버 컴포넌트가 자기 서버의 `/api` 를
  fetch 하면 왕복이 한 번 더 생긴다. `/api` 는 향후 모바일/외부용으로 남긴다
- **필터 상태는 URL 에.** 공유·뒤로가기·새로고침이 그대로 동작하고,
  서버에서 필터링하니 50개를 전부 클라이언트로 내려보낼 필요가 없다
- **enum 은 `import type` 만.** 라벨 맵이 Prisma 런타임을 클라이언트 번들로
  끌고 오지 않도록 했다
- **잘못된 쿼리 방어.** `?bodyPart=INVALID` 가 Prisma 까지 내려가면 500 이 난다.
  `pickEnum()` 으로 걸러 무시한다

React 관련 수정: URL → 입력창 동기화를 `useEffect` + `setState` 로 했더니
cascading render 경고가 떴다. **렌더 중 state 조정** 패턴으로 변경했다.

```tsx
if (syncedSearch !== currentSearch) {
  setSyncedSearch(currentSearch);
  setSearch(currentSearch);
}
```

### 4-7. 운동 기록 API

| 엔드포인트                                  | 설명                                     |
| ------------------------------------------- | ---------------------------------------- |
| `POST /api/workouts/sessions`               | 세션 시작                                |
| `GET /api/workouts/sessions`                | 지난 기록 목록 (페이지네이션, 기간 필터) |

| `PATCH /api/workouts/sessions/[id]`         | 종료 / 취소 / 메모                       |

| `DELETE /api/workouts/records/[id]`         | 운동 제거                                |
| `POST /api/workouts/records/[id]`           | 세트 추가                                |
| `PATCH`·`DELETE` `/api/workouts/sets/[id]`  | 세트 수정 / 삭제                         |
| `GET /api/workouts/last-record?exerciseId=` | 직전 기록 조회                           |

**하루 여러 번 운동** — `WorkoutSession` 에 날짜 유니크 제약이 없고 `startedAt`
(DateTime)을 쓰므로 자연히 지원된다. 대신 종료하지 않은 세션이 쌓이지 않도록
세션 시작 시 진행중 세션을 확인한다.

권장 흐름은 **시작 전에 먼저 물어보는 것**이다.

```
GET /api/workouts/sessions/active
          ↓
     진행중 있음?
      ↙        ↘
    YES         NO
     ↓           ↓
"이어서?"    POST (바로 시작)
  ↙   ↘
이어서  새로 시작
  ↓       ↓
기존 ID  POST mode:"new"
```

`active` 는 홈 화면의 "운동 중" 배너에도 쓴다. POST 만으로도 409 로 알 수 있지만,
그 경우 사용자가 이미 시작 버튼을 누른 뒤라 흐름이 끊긴다.

| mode         | 동작                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------- |
| `ask` (기본) | 진행중 세션이 있으면 **409 + activeSession** 반환 → 사용자에게 질문                                 |
| `resume`     | 기존 세션을 이어서 사용                                                                             |
| `new`        | 기존 세션을 마감하고 새로 시작. **기록이 없으면 CANCELLED** 로 정리해 빈 세션이 이력에 남지 않게 함 |

> `new` 로 기존 세션을 마감하는 이유: `getActiveSession` 은 `findFirst` 라서
> IN_PROGRESS 가 둘 이상이면 나머지는 영영 조회되지 않는 유령 세션이 된다.
> 기본값이 `ask` 라 자동으로 마감되는 일은 없고, 사용자가 "새로 시작" 을
> 명시적으로 고른 경우에만 동작한다.

**이전 기록 불러오기** — 운동을 추가하면 응답에 `previousRecord` 가 함께 온다.
클라이언트가 추가 호출 없이 값을 채울 수 있다.

```json
{ "record": { ... },
  "previousRecord": { "performedAt": "...", "maxWeight": 70,
                      "totalVolume": 1580, "sets": [...] } }
```

이 조회가 `WorkoutRecord.userId` 비정규화의 이유다. 세션을 조인하면
`[exerciseId, createdAt]` 인덱스가 **전체 사용자**의 기록을 훑는다.
운동은 50종뿐이라 카디널리티가 낮아 사용자가 늘수록 무의미해진다.

```prisma
@@index([userId, exerciseId, createdAt(sort: Desc)])
```

**주의해서 처리한 것**

- **Decimal 직렬화** — `weight` / `totalVolume` / `rpe` 는 Prisma Decimal 이라
  JSON 에서 **문자열**이 된다(`{"w":"62.5"}` 로 실측 확인). DTO 경계에서
  `Number()` 변환. 안 하면 프론트에서 `"62.5" + 5 = "62.55"` 가 된다
- **totalVolume 재계산** — 세트 추가/수정/삭제와 **같은 트랜잭션**에서 갱신.
  완료(`completed`)한 세트만 합산한다
- **setNumber 재정렬** — `(recordId, setNumber)` 유니크 제약 때문에 세트 삭제 후
  번호를 다시 매긴다. 오름차순으로 내려 쓰면 목표 번호가 항상 먼저 비어 충돌하지 않는다
- **소유권 검증** — 모든 조회/변경 쿼리의 `where` 에 `userId` 를 넣어
  남의 세션·기록·세트에 접근하면 404
- **API 인증** — `dal` 의 `requireUser` 는 `redirect()` 를 호출해 API 에서 쓰면
  JSON 대신 리다이렉트가 나간다. `app/api/_lib/api.ts` 의 `requireApiUser()` 가
  **401 JSON** 을 반환한다

### 4-8. 레이아웃 셸 + 홈

`app/(user)/layout.tsx` 가 **모바일 셸을 혼자 책임진다.**

- `max-w-md` 중앙 정렬 (데스크톱에서 폭이 늘어지지 않게)
- 하단 탭 5개: 홈 / 운동 / 캘린더 / 알림장 / 내정보
- 하단 여백 `calc(4.25rem + env(safe-area-inset-bottom))` — 아이폰 홈 인디케이터에
  버튼이 가리지 않도록

덕분에 하위 페이지는 `<main className="flex flex-col gap-N px-5 pt-N">` 만 쓰면 된다.
페이지마다 하단 여백을 다시 계산하면 언젠가 한 곳을 빠뜨린다.

캘린더는 별도 탭으로 뒀다. 홈에 주간 스트립을 넣고 캘린더를 홈 안에 접어 두면
"지난달 기록 보기"가 홈 스크롤 안에 묻힌다.

홈 구성: 인사 → 진행중 세션 배너(있을 때만) → 운동 시작 버튼 → 최근 7일 스트립 →
운동 라이브러리 링크. 준비 중인 탭(캘린더/알림장/내정보)은 빈 화면 대신
"준비 중" 안내를 띄운다.

**렌더 중 `Date.now()` 금지.** React 19 의 `react-hooks/purity` 규칙이 서버
컴포넌트에서도 이걸 에러로 잡는다. 경과 시간은 `toSessionDto` 가 `elapsedSec`
필드로 계산해서 내려준다. API 소비자에게도 필요한 값이라 설계상으로도 맞다.
클라이언트 타이머는 이 값을 초기값으로 받고 **마운트 이후부터만** 흐른다
(렌더 시점에 다시 계산하면 하이드레이션 불일치가 난다).

날짜 경계는 `lib/date.ts` 에서 **KST 고정**이다. Vercel 은 UTC 로 돌기 때문에
서버 로컬 시간으로 하루를 나누면 밤 9시 이후 운동이 다음 날 기록이 된다.

### 4-9. 세트 입력 화면

| 파일                                | 역할                             |
| ----------------------------------- | -------------------------------- |
| `app/(user)/workouts/[id]/page.tsx` | 세션 화면 (서버 컴포넌트)        |
| `add-exercise-drawer.tsx`           | 운동 검색 + 추가                 |
| `record-card.tsx`                   | 운동 카드 + `SetRow` 인라인 편집 |
| `actions.ts`                        | 서버 액션 6종                    |

**운동 추가는 Drawer 로.** `/exercises` 로 이동시키면 "어느 세션에 담는 중이었나"
라는 맥락이 끊긴다. 검색은 250ms 디바운스 + `AbortController` 로 이전 요청을 끊는다.

**세트 입력은 blur 에서만 저장한다.** 타이핑마다 서버 액션을 부르면 요청이
폭증한다. 값이 바뀌지 않았으면 아예 부르지 않는다. 반면 **완료 토글은 즉시** 저장한다
— 볼륨이 완료한 세트만 합산하므로 바로 반영돼야 한다.

**세트 행은 `set.id` 로 key 한다.** 삭제하면 서버가 `setNumber` 를 다시 매기는데,
번호로 key 하면 편집 중이던 입력값이 엉뚱한 행으로 옮겨 붙는다.

세트를 추가할 때 값은 `직전 세트 → 지난 기록의 첫 세트 → 빈 값` 순으로 채운다.
매번 60kg 을 다시 입력하게 만들면 안 된다. 운동마다 `getLastRecord` 를 **병렬로**
조회해 "지난 기록 60kg×10" 도 함께 보여준다.

종료된 세션은 입력 UI 를 감추고 값만 보여준다.

에러 처리는 `run()` 하나로 모은다. 서비스가 `null` 이면 "대상을 찾을 수 없습니다",
`WorkoutError` 면 그 메시지를 그대로, 나머지는 500 문구. 성공하면
`revalidatePath` 로 세션 화면과 홈을 갱신한다.

### 4-10. 운동 선택 (부위 칩 + 다중 선택)

검색만으로는 부족하다. **운동 이름을 모르는 사람은 검색을 못 한다.**

처음에는 "부위 목록 → 그 부위 운동" 2단계로 만들었는데, 레퍼런스 앱 화면을 보고
바꿨다. 검색창 아래 **가로 스크롤 칩 한 줄**(전체/가슴/등/…)이면 한 번만 누르면 된다.
운동이 0개인 부위는 칩 자체를 만들지 않는다 — 눌러서 빈 화면을 만나면 고장 난 걸로 보인다.
(시드 기준 `OTHER` 만 0개)

**다중 선택.** 하나 고를 때마다 드로어가 닫히면 "오늘 가슴 3개" 담는 데 같은 작업을
세 번 한다. 체크로 여러 개 고르고 하단 고정 버튼(`N개 추가`)으로 한 번에 담는다.

`addRecords()` 는 `orderIndex` 를 각각 계산하지 않는다. 따로 계산하면 같이 넣을 때
번호가 겹친다. 마지막 번호를 **한 번만** 읽고 이어 붙이며, 고른 순서를 유지한다.

**즐겨찾기**(`WorkoutFavorite`)는 모델만 있고 안 쓰이고 있었다. 매번 같은 5~6개를
하는 사람에게는 이게 사실상 첫 화면이다. 응답을 기다리면 별이 늦게 켜져 두 번 누르게
되므로 먼저 반영하고 실패 시 되돌린다.

> 검색 결과 0건에서 UI 가 깨지던 원인: **드로어 높이를 내용에 맡겼다.** 타이핑할수록
> 결과가 줄면서 드로어가 같이 줄고, 0개가 되면 납작해진다. `h-[85dvh]` 로 고정했다.

썸네일은 뺐다. `Exercise.thumbnailUrl` 필드는 있지만 시드에 값이 없어서
지금 넣으면 빈 네모 50개가 된다.

### 4-11. 기록 방식 두 축 (실시간 / 몰아서, 본인 / 트레이너)

운동하면서 실시간으로 적는 사람만 있는 게 아니다. 다 끝내고 앉아서 한 번에 넣는
사람에게 "시작 → 종료" 는 맞지 않고, **어제 운동은 아예 입력할 방법이 없었다.**

`WorkoutSession` 에 **서로 다른 축 두 개**를 넣었다. 하나로 합칠 수 없다.

| 필드               | 질문                | 값                        |
| ------------------ | ------------------- | ------------------------- |
| `entryMode`        | **어떻게** 입력했나 | `LIVE` / `MANUAL`         |
| `recordedByUserId` | **누가** 입력했나   | `null`=본인 / 트레이너 id |

**`entryMode` 가 필요한 이유.** 둘 다 편집하는 동안 `IN_PROGRESS` 여야 하는데,
구분이 없으면 어제 기록을 입력하는 중에 홈에 "운동 진행중" 타이머가 뜨고
새 운동 시작이 409 로 막힌다. `getActiveSession` 과 시작 충돌 검사를 `LIVE` 로 한정했다.

**`recordedByUserId` 가 필요한 이유.** 트레이너는 수업이 끝난 뒤에 적어 주므로
항상 `MANUAL` 이다. 그래서 축을 합치고 싶어지는데, 합치면 **어느 트레이너가 적었는지**
를 못 담는다. "김OO 트레이너가 기록" 표시도, 트레이너 화면의 "내가 적어 준 기록"
조회도 안 된다. 기록의 주인은 어디까지나 `userId` 의 회원이므로 트레이너 계정이
지워져도 기록은 남게 `SetNull`.

> 트레이너가 적는 도중에 회원에게 반쯤 적힌 기록이 보이면 안 되는데, 이건
> `IN_PROGRESS`(작성 중) → `COMPLETED`(전달됨) 로 이미 표현된다. 별도 필드가 필요 없다.

**MANUAL 의 시간 처리가 미묘하다.**

- 저장할 때 소요 시간을 **벽시계로 재지 않는다.** 그러면 *입력하는 데 걸린 시간*이
  운동 시간이 되고, 지난 날짜면 며칠짜리 운동이 된다. `durationSec` 은 비워 두고
  화면에는 `—` 를 보여준다
- `elapsedSec` 도 `null` 이다. `startedAt` 이 며칠 전이라 "3일 경과" 가 된다

같은 날짜를 다시 열면 **작성 중인** 세션을 재사용한다(매번 새로 만들면 입력하다
나갔다 온 사람에게 빈 세션이 쌓인다). 반면 이미 저장한 세션은 재사용하지 않는다 —
**하루에 두 번 운동한 걸 하나로 합치면 안 된다.**

### 4-12. 캘린더

`app/(user)/calendar/page.tsx`. 날짜를 누르면 그날 세션이 아래 목록으로 나온다.

- **하루에 두 번 운동할 수 있으니 항상 목록이다.** 기록이 있든 없든
  "이 날짜에 기록 추가" 를 함께 둔다. 빈 날에만 추가할 수 있게 하면
  오전에 하고 저녁에 또 한 사람이 막힌다
- `month` 와 `date` 를 **따로** 받는다. 하나로 묶으면 9월 30일을 고른 채 10월로
  넘겼을 때 선택이 화면 밖으로 사라진다
- 운동한 날은 **색이 아니라 점**으로 표시한다. 색만으로 구분하면 색각 이상이 있는
  사람이 구분하지 못한다
- `getMonthSummary` 는 세션 전체를 끌어오지 않는다. 점을 찍는 데는 날짜와 세트 수만
  있으면 되므로 `sets` 는 `_count` 로만 센다
- `IN_PROGRESS` 배지를 `입력 중`(MANUAL) / `진행 중`(LIVE) 로 구분한다

`buildMonthGrid` 는 앞뒤를 이전/다음 달 날짜로 채워 **항상 7의 배수**로 맞춘다.
빈 칸으로 두면 주 단위 줄이 어긋난다.

> 뒤를 채우는 반복문에서 `cells.length` 를 **루프 안에서 다시 읽어** 날짜가
> 건너뛰는 버그가 있었다(9/30 다음 칸이 10/4). 윤년·연말연시 포함 34개 케이스로
> 연속성을 검사해 잡았다.

### 4-13. 완료한 기록 수정

"종료" 는 운동이 끝났다는 뜻이지 **데이터가 굳었다는 뜻이 아니다.** 집에 와서 무게를
잘못 적은 걸 발견하는 일은 흔하다.

작업 중 **실제 구멍을 찾았다.** 상태 검사가 운동 추가에만 있고 세트 추가/수정/삭제와
운동 삭제에는 아예 없었다. 그래서 "종료된 세션에는 기록할 수 없습니다" 를 띄우면서도
세트는 고쳐졌고, **취소한 세션의 세트까지 수정됐다.** UI 가 가려서 안 보였을 뿐이다.

`assertEditable()` 한 곳으로 모아 다섯 군데에 모두 걸었다.

| 상태          | 수정                 |
| ------------- | -------------------- |
| `IN_PROGRESS` | 가능                 |
| `COMPLETED`   | **가능** ← 바뀐 부분 |
| `CANCELLED`   | 차단                 |

화면에서는 완료된 세션에 **`수정` 토글**을 둔다. 항상 입력칸을 띄워 두면 지난 기록을
훑어보다가 실수로 값이 바뀌는데 그게 더 나쁘다. 수정 모드에서는 운동 추가도 열어 준다 —
깜빡하고 안 적은 운동이 있다. 진행중 세션은 지금 입력하는 중이므로 토글 없이 늘 열려 있다.

**수정해도 `durationSec` 과 `status` 는 건드리지 않는다.** 나중에 고쳤다고 운동 시간이
다시 측정되면 안 된다.

### 4-14. 운동 요약 화면

종료하면 홈이 아니라 `/workouts/[id]/summary` 로 보낸다. 방금 한 운동이 어땠는지를
바로 보여줘야 다음에 또 열게 된다.

**신기록은 저장하지 않고 볼 때마다 계산한다.** 완료한 기록도 고칠 수 있으므로 박아 두면
값을 내려도 배지가 남는다. 비교 대상은 `startedAt` 이 앞선 세션뿐이다 — 몰아서 입력하면
만든 순서와 실제로 운동한 순서가 뒤집힌다.

처음 해 본 운동은 신기록이 아니라 **"첫 기록"** 이다. 전부 신기록이면 배지가 의미를 잃는다.

1RM 은 Epley (`w x (1 + reps/30)`) 를 쓰되 **12회를 넘으면 계산하지 않는다.** 20회를
환산해 신기록이라고 말하면 틀린 정보다.

### 4-15. 운동별 기록 추이

운동 상세에 "내 기록" 을 넣었다. 지난번에 몇 kg 을 들었는지 모르면 오늘 무게를 정할 수 없다.

작업 중 **요약과 추이가 서로 다른 말을 하는 걸 찾았다.** 요약은 첫 운동을 "첫 기록" 이라
하는데 추이는 "신기록" 이라고 했다. 판정 규칙을 한 곳으로 모았다.

**가장 무거운 세트가 곧 최고 1RM 이 아니다.** 65kg x 8회(82.3)가 70kg x 5회(81.7)보다
높다. 그래서 최고 중량과 최고 1RM 을 각각 집계 쿼리로 묻지 않고, 세트를 한 번만 가져와
함께 계산한다. 따로 물으면 두 값의 기준이 어긋난다.

차트 라이브러리는 넣지 않았다. 줄 뒤에 볼륨 비례 막대를 깔면 충분하고, 12줄을 그리려고
번들을 늘릴 이유가 없다.

### 4-16. 센터 소속과 초대 코드

**초대 코드는 관계가 아니라 임시 토큰이다.** 검증 -> 소속 생성 -> 사용 처리로 끝나고,
`CenterMembership` 이 실제 관계를 갖는다.

**코드 종류를 컬럼으로 두지 않았다.** 발급자(`createdBy.role`)에서 파생한다. 종류를 또
저장하면 `role` / `createdBy.role` / `type` 셋이 서로 어긋날 수 있다.

|                      | 발급자   | 자리수       | 결과                      |
| -------------------- | -------- | ------------ | ------------------------- |
| 트레이너 코드        | 관리자만 | **1로 강제** | 센터 소속 (담당 없음)     |
| 회원 코드 (관리자)   | 관리자   | 기본 50      | 센터 소속만               |
| 회원 코드 (트레이너) | 트레이너 | 기본 50      | 센터 소속 + **담당 배정** |

트레이너 권한은 남의 기록을 보므로 코드가 단톡방에 돌면 피해가 크다. 그래서 한 명만
쓸 수 있게 막았다.

**센터 가입과 담당 배정은 다른 관계다.** 관리자 코드로 들어오면 담당 트레이너는 비어 있다.
가입했다고 아무 트레이너에게나 붙이면 안 된다.

**담당 교체는 같은 센터의 다른 트레이너 코드를 넣는 것이다.** 트레이너가 바뀌는 건 예외가
아니라 일상인데 관리자를 거치게 하면 병목이 된다. 코드를 받아야 하므로 트레이너가 동의한
셈이기도 하다.

**프리랜서 트레이너는 1인 센터로 푼다.** `@@unique([centerId, userId])` 때문에 관리자와
트레이너 소속을 따로 가질 수 없어서, 권한을 포함관계로 뒀다 — `CENTER_ADMIN` 이
트레이너 기능도 쓴다 (`canActAsTrainer()`).

**나가도 행을 지우지 않는다.** PT 계약과 알림장이 이 소속을 참조하므로 지우면 지난 기록이
함께 사라진다. `LEFT` 로 남기고, 다시 들어오면 그 행을 되살린다.

**여러 센터는 아직 막아 두되 구조는 열어 뒀다.** 서비스는 전부 `membershipId` 를 받고
`getCurrentMembership()` 하나만 "한 곳뿐" 을 가정한다. 나중에 이 함수만 바꾸면 된다.

작업 중 **빌드는 통과하는데 요청하면 500 이 나는 결함**을 찾았다. `"use server"` 파일이
함수가 아닌 값(`OK` 상수)을 export 하고 있었다. 또 나가기 버튼을 화살표 함수로 감쌌더니
서버 액션 참조가 아니게 되어 `action="javascript:throw ..."` 로 그려졌다 —
자바스크립트가 없으면 동작하지 않는 폼이었다. 둘 다 브라우저로 눌러보기 전에는 안 보인다.

### 4-17. 알림장 · 공지 · 댓글

**알림장은 화면이지 저장소가 아니다.** PT 수업에서 한 운동의 원본은 `WorkoutSession` 이고
알림장은 그것을 트레이너의 글과 함께 보여줄 뿐이다. 알림장에 운동 내용을 따로 적어 두면
같은 사실이 두 곳에 저장되어 한쪽만 고쳐지는 순간 어긋난다.

**PT 수업 여부는 세션 단위로 표시한다.** `WorkoutSession.ptSessionId` (`@unique`, PTSession
과 1:1) 하나로 끝내고, 레코드에 있던 `ptSessionId` / `recordType` 과 `WorkoutRecordType`
enum 은 지웠다. 근거는 **누가 적었는지(`recordedByUserId`)가 이미 세션 단위**라는 것이다.
"PT 수업인가" 만 레코드 단위로 두면 두 축이 어긋나 "PT 세션인데 개인 기록", "회원이 적은
PT 기록" 같은 표현 불가능한 상태가 생긴다. 하루에 세션을 여러 개 만들 수 있으므로
PT 끝나고 혼자 유산소를 해도 세션이 나뉘어 섞이지 않는다.

**타임라인에 알림장 · 공지 · 내 운동을 섞는다.** PT 는 주 2회 정도라 알림장만 모으면 화면이
자주 빈다. 매일 열어볼 이유가 있어야 알림장도 읽힌다. 고정 공지(`pinnedAt`)만 날짜와
무관하게 맨 위에 둔다.

**공지 대상은 미리 펼치지 않고 읽을 때 계산한다.** `Notice` 하나에 대상자 수만큼 행을
만들면 나중에 들어온 회원이 지난 공지를 못 본다. `scope=CENTER` 면 센터 전체,
`TRAINER_MEMBERS` 면 작성자가 내 담당일 때만 보이도록 조회 조건으로 푼다.

**댓글을 `(targetType, targetId)` 공통 모델로 합치지 않았다.** 그렇게 하면 외래키를 걸 수
없어 알림장을 지워도 댓글이 남는다. `JournalComment` 로 따로 뒀다.

**읽음 표시를 넣었다.** 사용자는 상관없다고 했지만, 없으면 "오늘 확인할 것"을 고를 수 없어
알림장이 그냥 지나가는 화면이 된다. `Journal.memberReadAt` 은 상세를 열 때 기록하고,
`NoticeRead` 는 `upsert` 로 처음 연 시각을 유지한다.

**회원은 PT 운동 기록을 열람만 한다.** 트레이너가 적은 수업 기록을 회원이 고칠 수 있으면
기록의 근거가 사라진다.

여기서도 §4-16 과 **같은 결함이 재발했다** — 댓글 폼이 입력칸을 비우려고 서버 액션을
화살표 함수로 감싸는 바람에 자바스크립트 없이는 폼이 동작하지 않았다. 서버 액션을 그대로
넘기고, 성공할 때마다 바뀌는 `token` 을 입력칸의 `key` 로 걸어 비우는 방식으로 고쳤다.
타입 검사와 빌드로는 잡히지 않으므로 **히든 필드 유무를 검증에 넣었다.**

### 4-18. 트레이너 홈과 담당 회원

**목록이 아니라 할 일을 먼저 보여준다.** 트레이너가 하루에 여러 번 여는 화면이라
회원 이름만 스무 개 늘어놓으면 매번 눈으로 훑어야 한다. 오늘 수업이 있는 회원 →
답장을 기다리는 회원 → 나머지 순으로 정렬한다.

**"답장 대기" 를 읽음 표시로 풀지 않았다.** 트레이너에게 필요한 건 "봤는가" 가 아니라
"답했는가" 다. 그래서 컬럼을 새로 만들지 않고 **마지막 댓글이 회원 것인지**로 판단한다.
읽음 컬럼을 뒀다면 열어만 보고 답을 안 해도 목록에서 사라졌을 것이다.

**남의 담당 회원은 관리자에게도 열지 않았다.** 센터에 트레이너가 다섯이면 같은 센터라는
조건만으로 회원 스무 명의 기록이 전부 열린다. 관리자가 회원의 체중과 식단 사진을 볼
이유가 없고, 필요하면 담당으로 배정하면 된다.

**담당이 아닌 회원의 주소로 들어오면 404 를 준다.** "권한이 없습니다" 라고 알려주면
그 아이디의 회원이 존재한다는 사실 자체가 새어 나간다.

**차단을 레이아웃과 서비스 두 곳에서 한다.** 레이아웃의 검사는 화면을 숨기는 용도일 뿐이고
실제 차단은 서비스 함수마다 다시 한다. 주소만 알면 들어올 수 있는 화면이라 한 곳에서만
막으면 나중에 페이지를 하나 더 만들 때 새어 나간다.

**식단과 개인 운동기록은 아직 보여주지 않는다.** 공유 설정을 만들기 전까지는 회원이
동의한 적이 없다. 대신 화면에 "회원이 켠 항목만 나타난다" 고 적어 두었다. PT 수업 기록과
알림장은 원래 양쪽이 보는 것이라 지금도 보여준다.

**트레이너 화면에는 하단 탭을 두지 않았다.** 지금 갈 곳이 홈과 회원 상세뿐이라 탭이
비어 보인다. 대신 상단에 센터 이름과 "회원 화면" 전환 링크를 뒀다. 트레이너도 자기
운동을 기록하는 회원이라 두 화면을 오간다.

### 4-19. 알림장 작성과 사진 업로드

**사진은 브라우저에서 저장소로 바로 올린다.** 서버 액션 본문 한도가 기본 1MB 라 요즘 폰
사진(4MB)이 아예 들어가지 않고, 서버를 거치면 같은 파일이 올라갔다 내려가며 전송량을 두 배
쓴다. 서버는 서명된 업로드 주소만 만들어 준다.

**경로는 서버가 정한다.** 브라우저가 경로를 정하게 하면 남의 알림장 폴더에 올릴 수 있다.
붙이는 요청은 따로 들어오므로 붙일 때도 `journals/<알림장id>/` 로 시작하는지 다시 본다.

**버킷은 비공개다.** 회원의 몸 사진이 들어가는데 공개 버킷이면 주소만 알면 누구나 본다.
읽을 때마다 한 시간짜리 서명 주소를 만든다. 그래서 DB 에는 주소가 아니라 **저장소 경로**를
넣는다(`storagePath`). 서명된 주소를 저장하면 한 시간 뒤에 죽은 값이 남는다.

**올리기 전에 브라우저에서 줄인다.** 긴 변 1600px WebP 로 4MB 사진이 300KB 안팎이 된다.
목록용 480px 썸네일도 같이 만든다. 안 줄이면 회원 한 명당 수업마다 20MB 씩 쌓이고
트레이너 데이터 요금도 그만큼 나간다.

**`next/image` 를 쓰지 않았다.** 서명 주소는 열 때마다 값이 달라 최적화 캐시가 매번
빗나가고 그때마다 원본을 다시 받는다. 이미 줄여서 저장하므로 최적화로 얻을 것도 없다.

**사진을 지우면 저장소에서도 지운다.** DB 만 지우면 아무도 못 보는 파일에 요금이 계속
나간다.

**초안을 먼저 만들고 시작한다.** 사진을 올리려면 붙일 곳이 먼저 있어야 한다. 눌렀다 그냥
나가면 빈 초안이 쌓이므로, 같은 수업(수업이 없으면 같은 날)의 초안이 있으면 그걸 다시 연다.

**게시한 뒤에도 고칠 수 있다.** 오타 하나 때문에 지우고 새로 쓰면 회원이 단 댓글이 함께
사라진다. 다만 되돌려 초안으로 만들지는 않는다 — 회원이 이미 읽은 글이 목록에서 사라지는
게 더 이상하다. 게시한 글은 지울 수도 없다.

**저장과 게시를 한 폼에 뒀다.** 버튼마다 폼을 나누면 방금 친 내용이 다른 폼에 들어 있어서
저장을 눌렀을 때 사라진다. 사진만 폼 밖에 있다 — 파일은 이미 저장소에 올라가 알림장에
붙어 있어서 같이 보낼 이유가 없다.

**자바스크립트가 없으면 사진만 못 올린다.** 글쓰기 · 저장 · 게시 · 초안 삭제는 전부
서버 액션 폼이라 그대로 동작한다.

### 4-20. 홈 주간 캘린더에서 그날 기록 펼치기

**7칸을 링크로 바꿨다.** 그전에는 "운동한 날" 표시만 되고 눌러도 아무 일이 없었다.
운동했다는 건 알겠는데 뭘 했는지 보려면 캘린더 탭으로 넘어가 같은 날을 다시 찾아야 했다.

**주소로 상태를 남긴다**(`/home?day=YYYY-MM-DD`). 클라이언트 상태로 열면 상세를 봤다가
뒤로 오면 접힌 채로 돌아온다. 서버에서 그리므로 자바스크립트 없이도 열린다.

**화면에 그린 7일만 연다.** 주소로 들어오는 값이라 그대로 믿지 않는다. 아무 날짜나
열어 주면 홈이 캘린더 노릇을 하게 되는데 그건 캘린더 탭이 할 일이다. 형식이 틀리거나
범위 밖이면 조용히 무시하고 안 연 상태로 그린다(에러 화면을 띄울 만한 일이 아니다).

**한 번 더 누르면 닫힌다.** 열기만 되면 잘못 눌렀을 때 빠져나갈 방법이 없다. 고른 칸의
링크는 `/home` 을 가리키고, 패널에도 닫기 버튼을 뒀다.

**운동 이름만이 아니라 세트까지 줄여서 보여준다**(`40kg × 10회 3세트`). 이름만 나열하면
"뭘 했는지" 는 알아도 "얼마나 했는지" 는 모른다. 다만 세트마다 무게나 횟수가 다르면
하나로 못 줄이므로 세트 수만 말한다. 억지로 평균을 내면 실제로 하지 않은 무게가 뜬다.

**기록이 있어도 추가할 수 있다.** 하루에 두 번 운동하는 사람이 있다. 캘린더 탭과 같은
`LogPastWorkoutButton` 을 날짜를 고정해 붙였다.

### 4-21. 운동 라이브러리를 기록의 출발점으로

**"이 운동 기록하기" 를 운동 상세에 넣었다.** 그전에는 운동을 찾아 놓고도 홈으로 돌아가
"운동 시작 → 운동 추가 → 검색 → 이 운동 찾기" 를 다시 해야 했다. 방금 보고 있던 운동을
처음부터 다시 찾는 셈이다.

**진행 중인 운동이 있으면 거기에 넣는다.** 새 세션을 만들면 하루가 둘로 쪼개지고 진행 중
타이머도 둘이 된다. 이미 들어 있는 운동이면 또 넣지 않고 그리로 보내기만 한다. 버튼 글씨도
상황에 따라 바뀐다("이 운동 기록하기" / "오늘 운동에 추가하기" / "오늘 운동에서 이어서 하기").

**즐겨찾기 하트를 운동 상세에도 달았다.** 즐겨찾기 자체는 운동 추가 드로어에 이미 있었지만
(`server/workouts/favorite.service.ts`), 정작 운동을 자세히 보는 화면에서는 넣을 수 없었다.

**폼은 "뒤집어라" 가 아니라 "이렇게 만들어라" 를 보낸다**(`setFavorite`). 드로어처럼 화면이
현재 상태를 들고 있는 곳에는 `toggleFavorite` 이 맞지만, 새로고침으로 되돌아오는 폼에서는
두 번 눌리거나 화면이 두 개 열려 있을 때 누른 횟수에 따라 결과가 달라진다.

**운동 목록에 `[전체] [즐겨찾기]` 탭.** `getExercises` 에 `favoriteOfUserId` 를 더했다.
값이 없으면 거르지 않는다 — 실수로 빈 목록이 나오지 않게. 탭을 옮겨도 검색어와 부위 조건은
남고, "필터 초기화" 도 탭은 건드리지 않는다. 탭은 필터가 아니라 보는 범위다.

**"내 기록" 을 운동 방법 아래로 내리고 다섯 줄만 편다.** 처음 하는 운동일수록 방법이
궁금한데 기록이 위를 다 먹고 있었다. 나머지는 `?records=all` 로 편다. 접었다 폈다 해도 막대
길이의 기준은 전체 그대로다 — 기준이 바뀌면 늘었는지 줄었는지를 눈으로 못 읽는다.

**운동 상세 하단의 "요약 보기" 버튼을 없앴다.** 세트를 다 보고 있는데 한 번 더 눌러 비슷한
걸 보게 할 이유가 없다. 대신 요약에만 있던 **신기록 배지를 상세 위쪽으로** 옮겼다. 요약
화면 자체는 남는다 — 운동을 끝낸 직후 한 번 보는 화면으로는 여전히 값을 한다. 배지는 끝난
운동에만 붙인다. 진행 중에는 세트가 계속 바뀌어 배지가 붙었다 떨어졌다 한다.

### 4-22. 홈의 새 소식 · 최근 운동, 그리고 PT / 개인 운동 구분

**"새로운 소식" 은 읽을 게 있을 때만 그린다.** "새 소식 0개" 는 알려 주는 게 아니라 자리만
차지한다. 알림장과 공지를 나눠 적는다 — 합쳐서 "2" 라고만 하면 눌러 열기 전까지 무엇이
왔는지 모른다. 센터에 속하지 않은 사람에게는 아예 안 뜬다.

**세는 건 `getUnreadCounts` 로 따로 판다.** `getTimeline` 은 알림장 · 공지 · 운동을 30개씩
끌어와 섞는다. 홈에서 필요한 건 숫자 둘뿐이라 `count` 두 번으로 끝낸다.

**"최근 운동" 3개를 붙였다.** 주간 스트립은 "며칠 했는가" 만 말한다. 무엇을 했는지는 날짜를
눌러야 나오는데, 지난 운동을 이어서 하려는 사람은 대개 날짜를 기억하지 못한다.
`listSessions` 는 세트까지 전부 끌어오므로 홈에 쓰기엔 무겁다. `getRecentSessions` 는
운동 이름과 세트 개수만 센다.

**PT 와 개인 운동을 표시로만 나눈다.** DB 에서는 `WorkoutSession.ptSessionId` 로 이미
연결돼 있다. "PT 기록을 개인 기록에도 추가" 같은 복사 버튼은 만들지 않았다. 복사하면 같은
운동이 두 번 남아서 이번 주 몇 번 했는지부터 어긋난다. 화면에서는 한 목록에 함께 보여준다 —
사용자가 알고 싶은 건 "오늘 내가 무슨 운동을 했는가" 이지 어느 표에 들어 있는가가 아니다.

**색만으로 나누지 않는다.** 아이콘과 색을 바꾸는 동시에 "PT" 라고 글자로도 적고, PT 라면
대신 적어 준 트레이너 이름을 함께 보여준다.

**달력 칸에서는 PT 를 속 빈 고리로 그린다.** 색을 하나 더 쓰면 개인 운동 점과 구분이 안
되고, 점을 두 개 찍으면 무슨 뜻인지 알 수 없다. 하루에 둘 다 했으면 PT 쪽으로 센다.
그리고 **범례를 달았다** — 안 적으면 아무 의미 없는 무늬다.


**운동 추가 드로어에서 이미 담긴 운동을 보여준다.** 그전에는 같은 운동을 또 골라도 아무
표시가 없어 같은 줄이 조용히 두 개 생겼다. 다만 **막지는 않는다** — 서킷으로 같은 운동을 두
번 돌리거나, 몰아서 입력할 때 오전 · 오후를 나눠 적는 사람이 있다. 목록에 "담김" 배지를
붙이고, 담기 직전에 "이미 담긴 운동 N개가 있어요" 라고 말한다. 누르는 순간이 아니라 담기
직전에 말해야 되돌리기 쉽다.

### 4-23. 회원이 무엇을 보여줄지 직접 고른다 (`TrainerSharingSetting`)

트레이너 회원 상세에 "식단과 개인 운동기록은 아직 보이지 않아요" 라는 자리만 잡아 두었던
것을 실제 기능으로 채웠다.

**설정은 계정이 아니라 센터 소속에 붙인다.** 헬스장을 옮기면 새 트레이너에게 지난 센터의
설정이 그대로 따라가면 안 된다. `TrainerSharingSetting.membershipId` 가 `CenterMembership`
을 `@unique` 로 가리키고 `onDelete: Cascade` 다.

**기본값을 항목마다 다르게 뒀다.** 식단과 식단 사진은 **켜짐**, 개인 운동 기록과 체중은
**꺼짐**. 회원이 식단을 올리는 이유가 대개 피드백을 받기 위해서라 기본이 꺼져 있으면 올려
두고 "왜 답이 없지" 하게 된다. 반대로 혼자 한 운동과 몸무게는 보여주려고 적는 게 아니다.

**PT 수업 기록은 공유 대상이 아니다.** 트레이너가 직접 적은 것이라 회원이 가릴 대상이
아니고, 애초에 알림장으로 양쪽이 같이 보는 것이다. 설정 화면에도 그렇게 적어 뒀다.

**게이트는 서비스가 지킨다.** `assertTrainerCanView(trainerUserId, memberMembershipId, kind)`
하나를 통과해야만 회원 기록을 읽을 수 있다. 화면마다 조건문을 흩뿌리면 언젠가 한 곳이
빠지고, 그 한 곳이 사고가 된다. 네 단계다 — ① 트레이너로 활동 중인 소속인가 ② 내 담당
회원인가(관리자도 예외 없음) ③ 아직 ACTIVE 인가 ④ 그 종류를 공유하기로 했는가.

**실패를 두 종류로 나눠서 답한다.** 앞의 셋은 `TrainerError` → 404 로 "없는 사람" 이라고
답하고, 마지막 하나만 "회원이 공유하지 않았어요" 라고 말한다. 담당 회원이라는 건 트레이너가
이미 아는 사실이라 숨길 이유가 없지만, 담당이 아닌 회원은 **존재 자체를 알려선 안 된다.**

**설정 행을 미리 만들지 않는다.** 없으면 `DEFAULT_SHARING` 을 그대로 쓴다. 가입할 때마다
행을 만들면 나중에 기본값을 바꿔도 이미 만들어진 회원에게는 반영되지 않는다.

**식단 사진은 식단에 딸린다.** 식단을 안 보여주면서 사진만 보여줄 수는 없다. 화면에서는
들여쓰기로 종속을 보이고, 저장할 때 서버가 `shareDiet && shareDietPhoto` 로 한 번 더
맞춘다 — 폼은 직접 만들어 보낼 수 있기 때문이다.

**담당 트레이너가 없어도 설정 화면은 연다.** 배정을 기다리는 동안 미리 정해 둘 수 있어야
하고, 배정된 순간부터 바로 적용된다. 대신 "아직 담당 트레이너가 없어요" 라고 알려 준다.

**저장 뒤 `?saved=1` 로 리다이렉트한다.** 자바스크립트 없이 폼만 보내면 화면이 그대로 다시
그려질 뿐이라 뭐가 달라졌는지 알 수 없다. 폼 자체는 서버 컴포넌트가 서버 액션을 직접 물고
그리고, 저장 버튼만 `useFormStatus` 로 분리해 두 번 눌리는 것을 막는다.

### 4-24. 회원이 올리고 트레이너가 답한다 (식단)

**PT 알림장은 트레이너가 쓰고 회원이 읽는 한쪽 방향이다.** 그것만 있으면 회원은 계속 받기만
한다. 식단은 회원이 먼저 말을 거는 첫 통로라서 먼저 만들었다.

**칼로리와 탄단지를 받지 않는다.** 회원이 직접 숫자를 적게 하면 아무도 안 적는다. 그렇다고
지금 자동으로 계산할 방법도 없다. 그래서 끼니 · 사진 · 무엇을 먹었는지 · 메모 넷만 받는다.
`DietRecord` 에 `calories/carbohydrate/protein/fat` 칸은 이미 있으니 나중에 식약처 식품
영양성분 공공데이터를 붙이면 그때 채운다. 그때는 한 끼에 음식이 여럿이라 `DietRecordItem`
자식 표가 필요한데, 지금의 `foodName` 자유 텍스트는 "회원이 적은 원문" 으로 그대로 남고 항목
행이 그 위에 얹히는 구조라 옮겨 담을 일이 없다.

**영양 분석을 붙이더라도 목적은 정확한 숫자가 아니라 트레이너가 말을 걸 실마리다.** 숫자
정확도로 경쟁하기 시작하면 전용 식단 앱을 이길 수 없고, 방향도 개인 기록 앱 쪽으로 끌려간다.

**사진을 기록보다 먼저 올린다.** 알림장은 초안(`DRAFT`)을 먼저 만들고 거기에 사진을 붙이지만
식단에는 상태 칸이 없다. 사진을 고르려고 빈 기록부터 만들면 도중에 나간 사람의 빈 줄이 쌓인다.
그래서 저장소 경로를 기록이 아니라 **사용자로 끊고**(`diets/{userId}/{uuid}.webp`) 등록할 때
경로만 폼에 실어 보낸다. 서버는 `photoPathOf()` 로 그 경로가 정말 이 사람 폴더인지 다시 본다.
브라우저가 보내는 값이라 남의 폴더를 적어 보낼 수 있기 때문이다. 올려만 놓고 등록하지 않으면
주인 없는 파일이 남는데 한 장에 300KB 안팎이라 지금은 두고 나중에 걷어낸다.

**`imageUrl` 칼럼을 `imagePath` + `thumbnailPath` 로 바꿨다**(`20260907090901_diet_photo_path`).
버킷이 비공개라 주소를 열 때마다 새로 서명해야 하는데, 주소를 통째로 저장하면 저장된 순간
만료된 주소가 된다.

**목록을 그릴 때 서명 주소를 한 번에 만든다**(`attachUrls`). 기록마다 따로 부르면 하루 네 끼를
여는 데 저장소 요청이 여덟 번 나간다.

**사진 공유가 꺼져 있으면 주소를 아예 만들지 않는다.** 만들어 두고 화면에서만 감추면 응답
어딘가에 주소가 남는다.

**사진도 글도 없으면 등록을 거부한다**(`DietError("EMPTY")`). 끼니만 저장된 빈 줄이 쌓이면
무엇을 먹었는지 아무도 알 수 없고, 트레이너에게는 알림만 가고 볼 것이 없다.

**공유가 꺼지면 트레이너는 피드백을 쓰지도 못한다.** 못 보는 것에 답을 달 수는 없고, 회원이
껐다 켜는 사이에 글이 끼어들면 회원에게는 없던 댓글이 갑자기 나타난다.

**트레이너용 통로는 전부 `assertTrainerCanView(..., "DIET")` 를 지난다.** 화면의 조건문으로
막으면 주소를 직접 치는 사람을 못 막는다.

**피드백은 쓴 트레이너만 지운다.** 회원의 글이 아니라 트레이너의 글이다.

**식단을 알림장 타임라인에 섞었다.** 이 서비스의 중심은 운동 라이브러리가 아니라 트레이너와
회원 사이의 공유다. 회원이 올린 것도 같은 흐름에 놓여야 알림장이 "트레이너가 쓰는 게시판" 이
아니라 양쪽이 오가는 곳이 된다. **피드백을 따로 줄로 만들지 않고 식단 줄에 붙였다.** 한 식단에
댓글이 셋 달리면 같은 사진이 네 번 나온다. 대신 **피드백이 달리면 그 줄의 날짜를 피드백 시각으로
올린다.** 사흘 전 식단에 오늘 답이 달렸는데 사흘 전 자리에 그대로 있으면 아무도 못 본다.

**안 읽음 표시는 일부러 미뤘다.** `DietFeedback` 에 읽음 칸이 없다. 읽음을 넣으려면 누가 언제
봤는지를 따로 쌓아야 하는데, 지금은 피드백 개수를 보여주는 것으로 충분하다.

**삭제 확인 창을 두지 않았다.** 가벼운 기록이라 잘못 지워도 다시 올리면 된다. 대신 지울 때
저장소 파일도 함께 지운다. DB 만 지우면 아무도 못 보는 파일에 요금이 계속 나간다.

**등록 화면에 "○○ 트레이너가 볼 수 있어요" 를 적는다.** 공유가 중심인 서비스에서 내가 올린 것이
누구에게 가는지 모르면 아무것도 못 올린다.

**실패는 주소에 코드로 싣는다**(`?error=empty`). `useActionState` 를 쓰면 자바스크립트가 없을 때
아무것도 안 보인다. 서버 문구를 그대로 주소로 나르지는 않는다. 링크 하나로 아무 문구나 띄울 수
있기 때문이다.

### 4-25. 트레이너를 센터에서 떼어낸다 (`TrainerProfile` 독립)

`TrainerProfile` 이 `CenterMembership` 에 매달려 있었다. 센터에 가입해야만 트레이너가 될 수
있다는 뜻이고, 1인 PT샵·프리랜서·방문 PT 는 쓸 방법이 없었다.

**`CenterMembership` 이 두 가지 일을 겸하고 있었다.** ① 이 사람이 이 센터 소속이라는 증명
② PT 관계에서의 신분증. ② 만 떼어냈다.

- 트레이너 신분증 = `TrainerProfile.id` (`userId @unique`)
- 회원 신분증 = `User.id`
- 담당 관계 = **`TrainerMemberConnection`** (`ACTIVE` / `ENDED`, `startedAt`, `originCenterId?`)

**코드를 두 종류로 나눴다.** 센터 코드는 소속만, 트레이너 코드(`TR` 접두사)는 담당 관계를
만든다. 입력 칸은 하나로 두고 서버가 접두사로 가른다. 사용자에게 "이건 무슨 코드인가요" 를
묻지 않기 위해서다.

**승인 단계는 없다.** 코드를 직접 건넨 시점에 이미 동의한 것이다. 승인을 넣으면 트레이너가
회원 앞에서 코드를 불러주고도 다시 휴대폰을 꺼내 수락을 눌러야 한다.

**끊었다 다시 이으면 같은 줄을 되살리되 `startedAt` 은 오늘로 다시 잡는다.** 예전 기록까지
거슬러 보이면 안 된다.

**트레이너가 센터를 나가도 연결은 안 끊는다.** 나가고도 계속 봐 주는 경우가 흔하다.

센터 화면은 지우지 않고 진입점만 감췄다. 표를 지우면 되살릴 때 마이그레이션을 또 써야 한다.

### 4-26. PT 계약을 센터 상품에서 떼어낸다

`PTContract.productId` 가 필수였고 `PTProduct.centerId` 도 필수였다. **무소속 트레이너는 PT
계약 자체를 만들 수 없었다.** 4-25 에서 고친 함정이 한 층 아래에 그대로 있었다.

- `productId` 를 선택으로 내리고 (`onDelete: SetNull`)
- `productNameSnapshot` → **`title`** 로 바꿨다. 상품이 없는데 "상품명 스냅샷" 은 거짓말이다
- **`priceSnapshot` 은 지웠다.** 결제는 센터·트레이너가 하던 대로 한다. 우리가 안 받는 돈을
  적어 두면 언젠가 그 숫자로 정산하려 든다

**`POSTPONED` 상태는 만들지 않았다.** 미룬 수업도 여전히 앞으로 할 수업이라 "다음 수업"
목록에 남아야 한다. 상태로 두면 미룬 순간 목록에서 사라진다. 대신 **`PTSessionReschedule`**
이력을 쌓는다. "회원이 세 번 미뤘다" 와 "트레이너 사정으로 밀렸다" 는 재등록 상담에서 완전히
다른 이야기인데, 안 남기면 둘 다 "일정 변경 3회" 로만 보인다.

**차감 여부(`deducted`)는 상태에서 파생하지 않고 그때 박는다.** 노쇼를 깎을지는 트레이너마다
다르고, 같은 사람도 상황에 따라 봐 준다. 파생하면 정책을 바꾼 순간 **지난 계약의 남은 횟수가
소리 없이 달라진다.**

**취소의 기본값은 차감 안 함.** 기본을 차감으로 두면 그냥 눌렀다가 회원 횟수가 줄어든다.

**`usedSessions` 는 캐시다.** `syncUsedSessions()` 한 곳에서만 `deducted: true` 를 세어 다시
맞춘다. 세는 곳이 여럿이면 언젠가 어긋난다.

**수업을 잡을 때는 `deducted` 와 `SCHEDULED` 를 함께 센다.** 차감된 것만 세면 20회 계약에
수업을 서른 개 잡을 수 있다.

**만료는 저장하지 않고 읽을 때 판단한다**(`isExpired`). 시간이 지나서 되는 일이라, 아무도
함수를 안 부르는 동안 만료일이 지나간다.

**결과를 적는 것은 예정 상태에서만 한다**(`requireOpenSession`). 검증하다 찾았다. 되돌리기만
운동 기록을 확인하고 있어서, **완료한 회차를 취소로 덮어쓰면 운동 기록이 취소된 회차에
매달렸다.** 고치려면 되돌리기를 먼저 눌러야 한다.

**회원 홈에 다음 PT 를 붙였다.** 트레이너만 일정을 아는 상태가 제일 이상하다. 회원은 자기가
언제 가는지 카톡을 뒤져서 확인하고 있었다. 지난 세 시간까지 함께 보여 준다. 오후 7시 수업이
7시 1분에 사라지면 수업 직전에 확인하려던 사람이 못 본다.

**시각 표기를 `Intl` 에 맡기지 않는다.** `ko-KR` 로 넘겨도 ICU 판에 따라 "오후" 대신 "PM" 이
나온다. 로컬과 배포판이 달라서 배포한 곳에서만 영어로 뜬다.

- 회원은 코드 발급 불가, 트레이너는 트레이너 코드 발급 불가, 남의 코드 취소 불가
- 트레이너는 자기 코드만 / 관리자는 센터 전체 코드 조회
- 소문자·하이픈·공백 정규화
- **폼에 `role=CENTER_ADMIN` 을 끼워 넣어도 거절** (화면에 없는 값도 서버가 막는지)
- 자바스크립트 없이 폼을 낸 것과 같은 방식(서버가 그린 히든 필드 그대로 제출)으로 검증

**알림장 / 공지 / 댓글** — 서비스 15 + 화면 6 + 서버 액션 4 + 화면 스모크 8 = 33개

- 타임라인에 알림장·공지·운동이 섞여 최신순으로 나옴
- 고정 공지는 날짜와 무관하게 맨 위
- 초안 알림장 · 미게시 공지 · 취소한 운동 세션은 안 보임
- 다른 트레이너의 담당 회원 공지, 다른 센터 공지는 안 보임
- 안 읽은 개수는 알림장 + 공지만 셈 (운동은 안 셈)
- 상세를 열면 읽음으로 바뀌고, 공지는 두 번 열어도 읽음 행이 하나
- 남의 알림장 · 초안 · 남의 트레이너 공지는 404
- 댓글은 회원 본인과 담당 트레이너만, 빈 댓글과 1000자 초과는 거절
- 지운 댓글은 상세에서 빠짐
- **댓글 폼에 히든 필드가 있는지 확인** (자바스크립트 없이 동작하는지)
- `journalId` 를 남의 것으로 바꿔 보내도 서버가 막음
- 세션 단위 PT 표시로 바꾼 뒤 `/home` `/calendar` `/exercises` `/workouts/[id]`
  `/workouts/[id]/summary` `/journal` `/profile` 전부 200

**트레이너 홈 / 담당 회원** — 서비스 17 + 화면 7 = 24개

- 회원 · 무소속은 트레이너 화면에 못 들어감, 회원이 `/trainer` 로 가면 `/home` 307
- 홈에 **내 담당 회원만** 나옴 (같은 센터의 다른 트레이너 회원은 안 보임)
- 남의 담당 회원 · 다른 센터 회원은 서비스에서 `NOT_MY_MEMBER`, 화면에서는 404
- 오늘 수업이 있는데 알림장이 없거나 초안이면 "남은 일", 게시하면 빠짐
- 마지막 댓글이 회원 것이면 답장 대기 → 트레이너가 답하면 빠짐 →
  **회원이 또 물으면 다시 대기로 돌아옴**
- 상세에 계약 남은 횟수(10 - 3 = 7)가 맞게 나옴
- 상세의 다가오는 수업에 지난 수업은 안 나옴
- 내 정보의 "트레이너 화면으로" 링크가 회원에게는 안 보임

**알림장 작성 / 사진 업로드** — 서비스 23 + 화면 9 = 32개
(실제 Supabase Storage 에 올리고 받아 확인)

- 쓰기를 시작하면 초안이 생기고, 같은 수업으로 다시 시작하면 **초안을 재사용**
- 남의 담당 회원으로는 시작 불가, 남의 수업은 연결 불가
- 내용이 비면 게시 거부 / 빈 내용도 임시 저장은 됨 / 빈 칸은 `null` 로 저장
- 초안은 회원에게 안 보이고, 게시하면 보임
- 게시 뒤 수정해도 **게시 시각은 안 바뀜**, 게시한 글은 삭제 불가
- 남의 트레이너 · 회원은 수정 불가
- **서명 주소로 실제 업로드 → 실제 다운로드까지 확인**
- **서명 없이 공개 주소로 받으면 실패** (비공개 버킷인지 확인)
- 이미지가 아닌 형식 거부, `journals/<다른id>/` 경로로는 붙일 수 없음
- 사진 10장 초과 거부, 지우면 **저장소에서도 사라짐**
- 편집 화면에 회원 접근 시 307, 없는 알림장은 404
- "새로 쓰기" · "임시 저장" · "게시하기" · "초안 삭제" 전부
  **자바스크립트 없이 낸 것과 같은 방식**으로 검증

**홈 주간 캘린더** — 12개

- 아무 날도 안 고른 홈에는 기록 칸이 안 열림
- 7칸이 링크이고, 운동한 날을 고르면 그날 세션과 상세 링크가 나옴
- 세트 요약이 `40kg × 10회 3세트` 로 줄어서 나옴
- 고른 칸은 `aria-current="date"` 이고 다시 누르면 닫힘
- 기록 없는 날은 "이 날은 기록이 없어요" + "이 날짜 기록하기"
- 기록 있는 날에도 "이 날짜에 기록 추가" 가 붙음
- 7일 밖 날짜 · `../etc` · `2026-13-99` · 빈 값은 **200 으로 조용히 무시**
- 남의 기록은 안 보이고, 로그인 안 하면 리다이렉트

**운동 라이브러리에서 기록 시작 · 즐겨찾기** — 20개

- 운동 상세에 하트와 "이 운동 기록하기" 가 있고, "요약 보기" 는 사라짐
- 하트 · 기록 버튼 모두 **자바스크립트 없이 낸 것과 같은 방식**으로 검증
- 즐겨찾기를 켜면 폼이 "빼기" 로 바뀌고 `aria-pressed="true"`
- **같은 폼을 두 번 내도 결과가 같음** (뒤집기가 아니라 지정이라서)
- 즐겨찾기 탭이 즐겨찾기만 보여주고, 비면 안내가 뜸, 남의 것은 안 보임
- 탭을 옮겨도 검색어가 남음
- 기록 버튼이 새 세션을 만들어 운동을 넣음
- 진행 중이면 **세션을 또 만들지 않고** 거기에 붙임
- 이미 들어 있는 운동은 **또 넣지 않음**
- 없는 운동 404, 비로그인 리다이렉트
- 기록 6회일 때 접으면 5줄, `?records=all` 이면 전부
- 운동 방법이 내 기록보다 위에 있음
- 끝낸 운동 상세에 "신기록 1개를 세웠어요" 가 뜨고, 요약 화면은 그대로 열림

**홈 새 소식 · 최근 운동 · PT 구분** — 15개

- 안 읽은 알림장과 공지를 나눠 세고("알림장 1개 · 공지 1개"), 읽으면 줄어듦
- 다 읽으면 카드가 **아예 사라짐**, 센터에 없는 사람에게는 안 뜸
- 최근 운동이 최신순, **진행 중인 운동은 안 들어감**, 기록이 없으면 칸도 없음
- PT 운동에 "PT" 배지와 "홍길동 트레이너" 가 붙고, 개인 운동에는 안 붙음
- 홈 주간 캘린더의 그날 기록에도 같은 배지
- 캘린더 달력 칸에서 PT 한 날은 속 빈 고리, 범례로 뜻을 적어 둠
- PT 한 날을 고르면 트레이너 이름이 보이고, 개인 운동만 한 날에는 없음
- 남의 PT 기록은 안 보임

**운동 추가 드로어의 중복 표시** — 4개

- 이미 담긴 운동 목록이 드로어로 넘어가고, 안 담은 운동은 들어가지 않음
- 운동을 더 담으면 목록도 늘어남
- **같은 운동을 또 담는 건 여전히 됨** (막지 않는다)

### 우선순위 2 — 센터 / 역할 / 공유

> 사용자와 합의한 결론이 한 번 더 정리됐다. 아래 내용이 최신이다.

**회원가입은 역할별로 나누지 않는다.** 이유는 §1 참고 — `User` 에는 role 이 없고
role 은 `CenterMembership` 에 있다. 가입 화면에 "관리자로 가입"을 두면 그대로
권한 상승 통로가 된다. 역할은 `CenterInvitation` 초대 코드로만 얻는다.
`CENTER_ADMIN` 은 초대로도 만들 수 없어 초기엔 수동 생성한다.

**공유 대상은 "관리자"가 아니라 담당 트레이너**(`assignedTrainerMembershipId`)다.
센터 관리자에게 회원의 식단 사진과 체중을 열어 주면 사고가 난다.

공유 방식은 **항목별 동의**로 간다. `TrainerSharingSetting` 같은 **별도 모델**로
관리한다. `WorkoutSession.isSharedWithTrainer` 처럼 기록마다 불리언을 붙이면
항목을 늘릴 때마다 컬럼을 늘려야 하고, 무엇보다 **회원이 기록할 때마다 스위치를
눌러야 해서 결국 아무도 안 켠다.** 설정은 **회원 × 트레이너 1개**로 둔다.

| 항목                           | 공유                   |
| ------------------------------ | ---------------------- |
| 식단 (사진 / 내용 / 시간)      | 선택                   |
| 체중 · 체성분                  | 선택                   |
| 운동 기록 · 중량 / 횟수 · 메모 | 선택                   |
| 개인 루틴                      | 선택                   |
| **PT 수업 운동 기록**          | **자동** (동의 불필요) |
| 트레이너가 쓴 일지             | 회원에게 공개          |

**PT 수업 기록만 예외**인 이유: 트레이너가 적어 준 기록을 회원이 다시 공유해 줘야
보인다면 말이 안 된다. 이건 스키마에 이미 있다 — `WorkoutRecord.ptSessionId`

- `recordType(PERSONAL | PT)`.

**기본값은 코드에 박지 않는다.** 기본 ON 은 결국 회원이 모르는 채로 공개되는 것이다.
대신 **트레이너와 연결되는 순간 "무엇을 공유할까요?" 화면을 한 번** 띄우고,
거기서 식단·체중을 미리 켜 둔 상태로 보여준다. 기본 ON 의 실익은 챙기면서
회원이 알고 켠 것이 된다.

**(4-23 에서 `TrainerSharingSetting` 으로 구현 완료. 아래는 남은 부분이다.)**

필요한 것:

- ~~`MemberDataConsent` (memberMembershipId, scope, enabled)~~ → `TrainerSharingSetting`
- `DataAccessLog` — 누가 언제 무엇을 봤는지. 회원이 직접 확인할 수 있으면
  동의 장벽이 크게 내려간다
- ~~`assertTrainerCanView(...)` **단일 게이트**~~ → `server/sharing/sharing.service.ts`

역방향(트레이너 → 회원)은 동의가 필요 없고 모델도 이미 있다

## 6. 참고한 서비스

### 워니노트 (wonynote.com) — 프리랜서 강사용 수업 관리 · 급여 정산 앱

FitNote 와 **보는 방향이 반대**다. 워니노트는 강사가 자기 일(수업 · 정산)을 관리하는 앱이고,
FitNote 는 회원의 운동 기록이 중심이며 트레이너는 거기에 붙는다. 그래서 정산 · 급여 쪽은
가져올 게 없지만, 다음은 참고할 만하다.

**바로 쓸 만한 것**

- **지난 기록 옮기기** — 달력에서 과거 날짜를 여러 개 골라 한 번에 등록. FitNote 에도
  `LogPastWorkout` 이 있지만 하루씩이다. 다른 앱에서 넘어오는 사람에게는 이게 첫 관문이다
- **정기 수업(매주 반복)** — PT 일정 CRUD 를 만들 때 처음부터 반복을 넣어야 한다.
  나중에 붙이면 이미 만든 단건 일정과 섞여 지저분해진다
- **한국 공휴일 자동 표시** — 캘린더에 넣기 쉽고 체감이 크다
- **월간 결산** — 매달 1일에 지난달을 한 장으로. FitNote 는 회원용으로 "이번 달 운동 N회,
  가장 많이 한 운동, 늘어난 중량" 이 되겠다

**나중에 고려**

- **수업 시퀀스(웜업/메인/쿨다운)** — FitNote 의 "루틴" 에 해당. 트레이너가 만든 시퀀스를
  회원에게 배정하는 흐름이 자연스럽다
- **근육 사전** — 운동 상세의 `targetMuscles` 를 눌러 들어가는 형태로 확장 가능.
  다만 콘텐츠 제작 비용이 크다
- **Before & After** — 회원 사진 타임라인. 공유 설정(`shareBody`)과 직접 연결된다
- **생체인증 잠금** — 회원 신체 정보를 다루므로 언젠가 필요하다

**참고만 (지금은 안 함)**

- 급여 정산 · 장소별 단가 · 인센티브 — 프리랜서 강사 대상이고, FitNote 는 센터 소속
  구조라 맞지 않는다. 다만 "센터 관리자가 트레이너별 수업 건수를 본다" 는 형태로는 언젠가
- 강사 포트폴리오 PDF — 트레이너 유입용 미끼로는 좋으나 우리 핵심이 아니다
- 태블릿 Split View — 웹이라 반응형으로 자연스럽게 해결된다

**가격 구조 참고** — 무료로 기본 기능을 다 열고, 월 3,900원 / 연 39,000원에 리포트 ·
내보내기 · AI 를 붙였다. 신규 2주 Pro 체험. 한국 개인 대상 앱의 현실적인 가격대다.
